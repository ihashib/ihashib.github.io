Core

Java Beans

  • Java beans are classes that have many objects into a single object for encapsulation. This enables software reusability.

Spring Beans

  • Spring beans are beans that are created, managed and destroyed by Spring Containers. We can inject beans into Spring Container using metadata (xml or annotation)

Bean Life Cycle

  • Bean life cycle is managed by the spring container. When we run the program then, first of all, the spring container gets started. After that, the container creates the instance of a bean as per the request, and then dependencies are injected. And finally, the bean is destroyed when the spring container is closed. Therefore, if we want to execute some code on the bean instantiation and just after closing the spring container, then we can write that code inside the custom init() method and the destroy() method.

3 ways of implementation

By XML
  • Create class and properties of the bean
  • Register the beans in the XML spring.xml file
  • Create driver to run the bean
By Programmatic approach
  • Create the bean and using spring interfaces and overrides, write your logic.
  • Register the bean in spring.xml file
  • Create driver to run the bean
Using Annotation
  • Use annotations while creating the bean
  • Register the bean in spring.xml file
  • Create driver to run the bean

  • DI is when a class cannot instantiate without another object that provides the necessary parameters.
  • The class itself does not have any responsibilities getting the dependencies.
  • DI is a RUNTIME process.

Spring IoC (Inversion of Control)

  • Is a technique to allow Dependencies to be injected runtime.
  • The dependency to be injected is not predetermined.
  • The framework can determine which dependency to inject.
  • Example: MySQL data source injection.
  • The framework should call the user defined methods instead of the user application. IoC allows frameworks to serve as extensible skeletons.

IoC vs DI

  • DI focuses on creating the dependent classes that require dependency injection. It is the process.
  • IoC is the runtime environment of the program, the DI classes are injected by the framework.

BeanFactory and Application Context

  • Spring's DI, the injection mechanism, is the concrete implementation of IoC. When you define a bean with @Bean annotation and Spring creates an instance based on it, you're delegating control of object creation to the container. Similarly, when Spring injects dependencies into other beans, it's taking control of how those dependencies are provided and managed.
  • So, IoC provides the overall principle of delegating control, while the injection mechanism in Spring's DI implements that principle in a specific way.
  • Here's an analogy to illustrate:
  • Imagine building a robot. In traditional coding, you'd directly create and assemble all the robot's parts (arms, legs, etc.). This is similar to having tight control over dependencies.
  • With IoC (and Spring's DI), it's like having a factory that manufactures individual parts and delivers them to you as needed. You simply specify what you need, and the factory takes care of creating and providing them. This translates to loose coupling and centralized configuration.
  • In essence, Spring's DI is built on the foundation of IoC, providing a practical and efficient way to achieve its benefits in your applications.

Spring AOP

Concerns

  • Concern in a system is a part that is divided by functionality.
  • Usually, code can be separated into logical sections, each addressing separate concerns.
Types

Core concerns

  • Core concerns represent single and specific functionality for primary requirements. e.g. business logic.

Cross-cutting concerns

  • These concerns are shared across multiple modules in the system, they are also called System wide concerns
  • Usually these are secondary functionality like Logging, Security, Data transfer.

AOP Architecture

  • Spring AOP is based on the proxy design pattern. This means, spring AOP creates proxy objects for the cross-cutting concern so that other concerns calling it have controlled access to it.
  • In runtime, spring analyzes cross-cutting concerns the ApplicationContext and generates proxy beans dynamically in runtime. The proxy bean for the cross-cutting concern is created only when it’s called by another object.
  • Spring has two proxy implementation
JDK dynamic proxies
  • When the target object advised implements an interface.
CGLIB proxies
  • When the target object advised does not implement an interface.

Limitations

  • Final or static can not be proxied.
  • Spring AOP only applies to public, non-static methods.

Terminologies

Joinpoint
  • Joinpoint in an application are the points where methods are called or exceptions are thrown.
  • In Spring AOP join points are always a method execution.
  • Join Points are the points where you can insert AOP logic.
Advice
  • Advice is the code that is executed at a join point.
  • There are 5 types of advice.

Before

  • Executed before a join point but can not prevent the execution of the join point.

After returning

  • Executed after a join point that does not throw an exception.

After throwing

  • Executed after a method throws an exception.

After

  • Executed after a join point (normal/exception throw)

Around

  • The most powerful advice.
  • Can perform custom behavior before and after the method execution.
  • Can change the flow of the join point and return/throw its own value.
Aspect
  • Aspects are encapsulated classes that contain the advice and pointcuts.
Weaving
  • is the process of inserting aspects into the application code at the appropriate point. AspectJ supports a weaving mechanism called load time weaving (LTW), in which it intercepts the underlying JVM class loader and provides weaving to the bytecode when it is being loaded by the class loader.
Target
  • Also known as the advised object, it’s the object that has its workflow modified by Spring AOP.

Web security 101

Authentication
  • Authentication is verifying that the user is the person they claim to be.
Authorization
  • Authorization is verifying access to the sub-systems.
Servlet filters
  • A Java servlet filter like dispatcher Servlet handles all HTTP requests but does not have security built into it.
  • We can write the security and configuration in the servlet container like Tomcat. So the security is handled before it reaches the dispatcher servlet.
  • Example:
    • HTTP request
    • First goes though the Login filter, that extracts the user credential
    • Then the Authentication filter checks if the user is valid.
    • After That, the Authorization filter checks the user’s access rights.
    • Finally, the request is sent to the dispatcher servlet.
    • These filters are chained thus known as Filter chains.

FilterChain & Security Configuration DSL

FilterChain
  • Spring Security is a collection of these filterchains.
  • There are 15 default filters in a spring boot application.
  • By default these filters are well configured but you can modify them to your application.
  • Some of the filters:
  • BasicAuthenticationFilter: Tries to find a Basic Auth HTTP Header on the request and if found, tries to authenticate the user with the header’s username and password.
  • UsernamePasswordAuthenticationFilter: Tries to find a username/password request parameter/POST body and if found, tries to authenticate the user with those values.
  • DefaultLoginPageGeneratingFilter: Generates a login page for you, if you don’t explicitly disable that feature. THIS filter is why you get a default login page when enabling Spring Security.
  • DefaultLogoutPageGeneratingFilter: Generates a logout page for you, if you don’t explicitly disable that feature.
  • FilterSecurityInterceptor: Does your authorization.
Security Configuration DSL
@Configuration
@EnableWebSecurity // (1)
public class WebSecurityConfig extends WebSecurityConfigurerAdapter { // (1)
 @Override
 protected void configure(HttpSecurity http) throws Exception{//(2)
     http
       .authorizeRequests()
         .antMatchers("/", "/home").permitAll() // (3)
         .anyRequest().authenticated() // (4)
         .and()
      .formLogin() // (5)
        .loginPage("/login") // (5)
        .permitAll()
        .and()
     .logout() // (6)
       .permitAll()
       .and()
     .httpBasic(); // (7)
 }
}


                           1. A normal Spring @Configuration with the @EnableWebSecurity annotation, extending from WebSecurityConfigurerAdapter.
                           2. By overriding the adapter’s configure(HttpSecurity) method.
                           3. All requests going to / and /home are allowed (permitted) - the user does not have to authenticate.
                           4. Any other request needs the user to be authenticated first, i.e. the user needs to login.
                           5. You are allowing form login (username/password in a form), with a custom loginPage (/login, i.e. not Spring Security’s auto-generated one). Anyone should be able to access the login page, without having to log in first (permitAll; otherwise we would have a Catch-22!).
                           6. The same goes for the logout page
                           7. On top of that, you are also allowing Basic Auth, i.e. sending in an HTTP Basic Auth Header to authenticate.

SOLID

Single responsibility principle

  • Every class should have a single responsibility
  • Classes should be small and big classes should be split into smaller classes.

Open closed principle

  • Classes should be open for extension but closed for modification.
  • Class’s behavior can be changed without modifying it.
  • Use getters and setters only when you need them.
  • Use abstract base classes
  • Example
  • We have a class student validator which works fine by itself but if we want to add another feature to validate faculties as well, we will have to modify the student validator to have different added methods and properties. Which defies the principle.

Liskov substitution principle

  • Objects in a program should be replaceable with instances of its subtypes without altering the correctness of the program.
  • Basically, when inheriting from a superclass, the inherited class should not change the properties or methods of the superclass that change the way they behave .
  • Example
  • The parent class requires one type of object but the child class requires another type of object in the constructor.

Interface segregation principle

  • Make fine grained interfaces that are client specific.
  • Many client specific interfaces are better than a general purpose big interface.
  • Keep components focused and minimize dependencies between them.
  • Make an interface plug and play.

Dependency inversion principle

  • Classes should be loosely coupled.
  • Abstractions should not depend on details and details should depend on abstraction.
  • Higher level and lower level objects should depend on the same abstract interaction.
Data: Hibernate and Mongo
Hibernate
  • The implementation.
  • The library that actually performs the logic, manages the database connection, generates SQL and maps results of objects.
  • Spring data JPA
  • The abstraction layer.
  • A framework that wraps hibernate. It significantly reduces boilerplate by providing “Repository” interfaces and generating implementation code at run time via Dynamic proxies.
  • Core Annotations:
  • @Entity: Marking classes as persistent entities.
  • @Id
  • Designates the Primary Key.
  • @GeneratedValue
  • GenerationType.IDENTITY: Relies on an auto-increment column (MySQL/Postgres). Disables JDBC batch inserts.
  • GenerationType.SEQUENCE: Uses a database sequence. Most efficient for high-performance batching (Oracle/Postgres).
  • GenerationType.UUID: Generates a specialized string UUID. Good for distributed systems (Microservices).
  • @Column
  • name: DB column name.
  • nullable: Adds NOT NULL constraint.
  • updatable=false: Useful for creation timestamps or IDs that shouldn't change.
  • @Transient
  • Fields ignored by the persistence engine (e.g., calculated fields like age derived from birthDate).
  • @Enumerated
  • EnumType.ORDINAL: Saves the index (0, 1). Brittle if enum order changes.
  • EnumType.STRING: Saves the name ("ACTIVE", "BANNED"). Readable but takes more space.
  • Inheritance Strategies
  • How to map Java Inheritance (Employee extends User) to SQL tables.
  • Single Table (Default)
  • One giant table for all subclasses with a "Discriminator Column" (e.g., dtype). Fast reads, but columns for subclasses must be nullable.
  • Joined
  • Separate tables for Parent and Child, joined by PK. Normalized, but slow writes/reads due to JOINs.
  • Table Per Class
  • One table per concrete class. No joins, but polymorphic queries (searching the Parent type) are very slow (UNION SQL).
  • Relationships:
  • @OneToOne: One entity has a single relationship with another entity.
  • @OneToMany: One entity has multiple relationships with another entity.
  • @ManyToOne: The inverse side of a @OneToMany relationship.
  • @ManyToMany: When entities have many-to-many relationships.
  • Basic CRUD operations:
  • Using an EntityManager (the key JPA interface) for:

Mongo GeoJSON (GIS)

Core Concepts

  • Coordinate Order
  • [Longitude, Latitude] (X, Y)
  • ⚠ Warning: Google Maps gives you [Lat, Long]. You must swap them for MongoDB/GeoJSON.
  • Winding Order (Polygons)
  • Counter-Clockwise (CCW): The filled area (The shape itself).
  • Clockwise (CW): The hole (Exclusion zone).
  • Indexing
  • @GeoSpatialIndexed(type = GeoSpatialIndexType.GEO_2DSPHERE)

Varieties

Point

  • A single specific location in space.
  • Structure
  • [Longitude, Latitude]
  • When to use
  • User location.
  • Store address.
  • Vehicle position.
  • Example
  • GeoJsonPoint
  • // x=Long, y=Lat
  • GeoJsonPoint point = new GeoJsonPoint(-73.93, 40.73);

LineString

  • An ordered list of two or more points forming a path.
  • Does not have to be closed.
  • Structure
  • [ [x,y], [x,y], [x,y] ]
  • When to use
  • GPS Route (Uber trip path).
  • Rivers.
  • Street segments.
  • Java Implementation
  • GeoJsonLineString
  • Example
  • List<Point> points = Arrays.asList(
  • new Point(-73.9, 40.7),
  • new Point(-74.0, 40.8)
  • );
  • GeoJsonLineString route = new GeoJsonLineString(points);

Polygon

  • A closed shape defining an area.
  • Structure
  • Ring 1 (Outer): The boundary (Must be CCW).
  • Ring 2+ (Inner): Optional holes (Must be CW).
  • Rules
  • Closed Loop: First and Last point must be identical.
  • Minimum Points: 4 points (3 to make a triangle + 1 to close loop).
  • When to use
  • City boundary.
  • A specific park.
  • A Geofence.
  • Example
  • GeoJsonPolygon
  • // Define points (Last point == First point)
  • Point p1 = new Point(0,0);
  • Point p2 = new Point(0,10);
  • Point p3 = new Point(10,10);
  • Point p4 = new Point(10,0);
  • // CCW order
  • GeoJsonPolygon poly = new GeoJsonPolygon(p1, p2, p3, p4, p1);

MultiPoint

  • A collection of points treated as a single document/entity.
  • Structure
  • [ [x,y], [x,y], ... ]
  • When to use
  • "All bus stops for Route 55" (stored as one object).
  • Scattered data points belonging to one dataset.
  • Example:
  • GeoJsonMultiPoint
  • List<Point> stops = Arrays.asList(point1, point2, point3);
  • GeoJsonMultiPoint busStops = new GeoJsonMultiPoint(stops);

MultiLineString

  • A collection of LineStrings that are not connected.
  • Structure
  • Array of LineString arrays.
  • When to use
  • A road network with gaps.
  • A river system with tributaries (where lines branch off).
  • Example
  • GeoJsonMultiLineString
  • List<GeoJsonLineString> lines = Arrays.asList(routeA, routeB);
  • GeoJsonMultiLineString network = new GeoJsonMultiLineString(lines);

MultiPolygon

  • A collection of disjointed Polygons treated as one entity.
  • Structure
  • Array of Polygon arrays.
  • When to use
  • Countries with islands (USA = Mainland + Hawaii + Alaska).
  • A delivery zone that covers two separate neighborhoods.
  • Example
  • GeoJsonMultiPolygon
  • List<GeoJsonPolygon> areas = Arrays.asList(downtown, airport);
  • GeoJsonMultiPolygon serviceZone = new GeoJsonMultiPolygon(areas);

GeometryCollection

  • A mixed bag of different geometry types in one object.
  • Can contain a Point AND a LineString AND a Polygon.
  • Structure
  • geometries: [ {type: "Point"...}, {type: "Polygon"...} ]
  • When to use
  • Complex CAD drawings.
  • A "Feature" that includes a station (Point) and the track leading to it (LineString).
  • Note: Less common in standard "Find nearby" queries.
  • Example
  • GeoJsonGeometryCollection
  • List<GeoJson<?>> mixed = Arrays.asList(myPoint, myPolygon);
  • GeoJsonGeometryCollection collection = new GeoJsonGeometryCollection(mixed);
