Spring Initializr

The quickest way to start a Spring Boot project is start.spring.io (source code). IntelliJ IDEA Ultimate has the same form under New Project → Spring Boot.

A good starting setup:

Option Pick
Project Maven
Language Java 17 or newer
Spring Boot the latest stable 3.x
Dependencies Spring Web, Spring Data JPA, a database driver (H2 to start, MySQL later), Lombok

Click Generate, unzip, and open the folder in your IDE.

Maven, the database and the JDK

Connect a database

In src/main/resources/application.properties:

spring.datasource.url=jdbc:mysql://localhost:3306/shop
spring.datasource.username=root
spring.datasource.password=secret
spring.jpa.hibernate.ddl-auto=update   # create and update tables from your entities

The database (shop here) must already exist.

Maven commands

mvn clean package            # delete old build output, compile, test, make the .jar
mvn test                     # run the tests
mvn test -pl orders-service  # tests of one module only
mvn spring-boot:run          # start the app
java -jar target/app.jar     # run the built jar

Maven builds the runnable jar itself, so there's no need to set up IntelliJ's Artifacts.

Choose the Java version

sudo update-alternatives --config java              # pick the default java
export JAVA_HOME=/usr/lib/jvm/jdk-17-oracle-x64     # the JDK Maven uses
Building a web app4 topics

JPA entities

Databases store tables; Java has objects. An ORM (object–relational mapping) translates between them, so you work with objects and it writes the SQL.

An entity

Mark a class with @Entity and it becomes a table; each field becomes a column.

@Entity
public class Author {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;              // every entity needs a primary key

    private String firstName;
    private String lastName;

    protected Author() {}         // JPA needs an empty constructor

    public Author(String firstName, String lastName) {
        this.firstName = firstName;
        this.lastName = lastName;
    }
    // getters, setters, equals/hashCode and toString
    // (or Lombok's @Getter @Setter to skip the typing)
}

An entity is a POJO (Plain Old Java Object): just fields, constructors and getters/setters, no framework base class.

Relationships

@ManyToMany
@JoinTable(name = "author_book",
           joinColumns = @JoinColumn(name = "author_id"),
           inverseJoinColumns = @JoinColumn(name = "book_id"))
private Set<Book> books = new HashSet<>();

More on relationships in Hibernate below.

Repositories

A repository gives you saving, finding and deleting without writing SQL. You write an interface; Spring writes the class at runtime.

public interface AuthorRepository extends JpaRepository<Author, Long> {   // <entity, id type>

    List<Author> findByLastName(String lastName);              // Spring writes the query from the name
    List<Author> findByFirstNameContainingIgnoreCase(String s);

    @Query("SELECT a FROM Author a WHERE size(a.books) > :n")  // JPQL, for anything harder
    List<Author> prolific(@Param("n") int n);
}

authorRepository.save(new Author("Humayun", "Ahmed"));
authorRepository.findById(1L);   // Optional<Author>
authorRepository.findAll();
authorRepository.deleteById(1L);

MVC: Model, View, Controller

MVC splits a web app into three jobs. In a restaurant:

Part Job Restaurant
Model The data and the rules The kitchen
View What the user sees (an HTML page, or JSON) The plate in front of you
Controller Takes the request, asks the model, picks the view The waiter

How Spring does it

Spring MVC uses a front controller: one servlet, the DispatcherServlet, receives every request and passes it on.

  1. The DispatcherServlet receives the HTTP request.
  2. It finds the controller method mapped to that URL (its handler mapping).
  3. The controller does its work, usually through a service, and returns a model and a view name (or an object to turn into JSON).
  4. The DispatcherServlet renders the view and sends the response.

MVC in plain Java

The same idea without Spring:

class Student {                         // Model
    private String name;
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
}

class StudentView {                     // View
    public void print(String name) { System.out.println("Name: " + name); }
}

class StudentController {               // Controller
    private final Student model;
    private final StudentView view;

    StudentController(Student model, StudentView view) { this.model = model; this.view = view; }

    public void setName(String name) { model.setName(name); }
    public void updateView() { view.print(model.getName()); }
}

Controllers

@Controller marks a class as a Spring bean that handles web requests; @GetMapping, @PostMapping and friends map methods to URLs.

Returning a page

@Controller
public class BookController {

    private final BookRepository bookRepo;

    public BookController(BookRepository bookRepo) {   // injected by Spring
        this.bookRepo = bookRepo;
    }

    @GetMapping("/books")
    public String list(Model model) {
        model.addAttribute("books", bookRepo.findAll());
        return "books";             // the template books.html renders the list
    }
}

Returning JSON (a REST API)

@RestController = @Controller + @ResponseBody on every method: return values become JSON.

@RestController
@RequestMapping("/api/books")
public class BookApi {

    @GetMapping("/{id}")                      // GET /api/books/7
    public Book one(@PathVariable Long id) { ... }

    @GetMapping                               // GET /api/books?author=Rafi
    public List<Book> byAuthor(@RequestParam String author) { ... }

    @PostMapping                              // the JSON body becomes a Book
    public Book create(@RequestBody Book book) { ... }
}
Annotation Reads
@PathVariable A part of the path: /books/{id}
@RequestParam A query parameter: ?author=Rafi
@RequestBody The request body (JSON)
@RequestHeader A header
@ModelAttribute Form fields, bound to an object
Spring core and design7 topics

Beans, dependency injection and IoC

A guided path through the whole ecosystem: Spring Boot roadmap.

Beans

A Spring bean is an object that Spring creates, wires up and destroys for you. You declare beans with annotations (@Component, @Bean); older projects used XML.

Dependency injection (DI)

A class shouldn't build the things it needs; it should receive them. Then you can swap the implementation (email, SMS, a fake for tests) without touching the class.

1. A service interface and its implementations

public interface MessageService {
    void send(String from, String to);
}

@Component
class EmailService implements MessageService {
    public void send(String from, String to) { System.out.println("Email " + from + " → " + to); }
}

2. A consumer that depends on the interface, not on a class

@Component
class PotterMail {
    private final MessageService service;

    PotterMail(MessageService service) {      // constructor injection
        this.service = service;
    }

    void process(String from, String to) { service.send(from, to); }
}

3. The container wires them together

@Configuration
@ComponentScan("com.example.mail")
public class AppConfig {}

public class Main {
    public static void main(String[] args) {
        var context = new AnnotationConfigApplicationContext(AppConfig.class);
        context.getBean(PotterMail.class).process("harry@hogwarts.uk", "ron@hogwarts.uk");
    }
}

What happens: Spring reads AppConfig, scans the package, and creates an EmailService bean. When it builds PotterMail, it sees the constructor needs a MessageService, finds the one bean that implements it, and passes it in.

Three ways to inject

Way Verdict
Constructor Use this. Fields can be private final, and the class is easy to test.
Setter Only for optional dependencies
Field (@Autowired on a field) Avoid: hidden dependencies, hard to test

Good habits: inject through constructors, make injected fields private final, and depend on interfaces rather than concrete classes.

Inversion of control (IoC)

Normally your code calls libraries. With IoC, the framework calls your code: it decides when to create objects and which implementation to use (say, which DataSource). DI is the way Spring achieves IoC.

Analogy: without IoC you build every robot part yourself. With IoC there's a factory: you say what you need and the parts are delivered.

The container comes in two forms: BeanFactory, the basic one, and ApplicationContext, which adds events, internationalisation and AOP. You'll almost always use ApplicationContext.

Core annotations

Annotation Meaning
@Component "Make a bean of this class"
@Service, @Repository, @Controller The same, with a role (@Repository also translates database errors)
@Configuration A class that declares beans with @Bean methods
@Bean This method returns a bean
@ComponentScan Where to look for components (default: this package and below)
@PropertySource Load a .properties file
@SpringBootApplication @Configuration + @EnableAutoConfiguration + @ComponentScan

Init and destroy hooks

@Configuration
public class AppConfig {
    @Bean(initMethod = "on", destroyMethod = "off")
    Computer computer() { return new Computer(); }
}

or, inside the bean itself:

public class Computer {
    @PostConstruct void on()  { System.out.println("Load operating system"); }
    @PreDestroy    void off() { System.out.println("Close all programs"); }
}

Aspect-oriented programming (AOP)

Some code is needed everywhere: logging, security checks, transactions. These are cross-cutting concerns, as opposed to core concerns (the business logic). AOP keeps them in one place instead of copying them into every method.

Term Meaning
Join point A point where extra code can run. In Spring: always a method call.
Advice The extra code
Pointcut An expression that picks the join points, e.g. "every method in the service package"
Aspect A class holding advice and pointcuts
Target The object whose methods are advised
Weaving Attaching aspects to targets. Spring does it at runtime with proxies; AspectJ can also do it while classes load.

Kinds of advice

Advice Runs
@Before Before the method (can't stop it, except by throwing)
@AfterReturning After it returns normally
@AfterThrowing After it throws
@After After it finishes, either way
@Around Around it: can run code before and after, change the result, or skip the call 
@Aspect
@Component
public class Timing {
    @Around("execution(* com.example.service.*.*(..))")
    public Object time(ProceedingJoinPoint jp) throws Throwable {
        long start = System.nanoTime();
        try {
            return jp.proceed();                 // call the real method
        } finally {
            System.out.println(jp.getSignature() + " took " + (System.nanoTime() - start) / 1_000_000 + " ms");
        }
    }
}

Add spring-boot-starter-aop; Boot turns it on (otherwise use @EnableAspectJAutoProxy).

How the proxy is made: a JDK dynamic proxy if the bean implements an interface, otherwise a CGLIB subclass.

Limits: only public, non-static methods called from outside the bean are advised; final classes and methods can't be proxied.

Bean scopes

Scope Instances
singleton (default) One for the whole app, shared by everyone
prototype A new one every time it's requested
request One per HTTP request
session One per user session
application One per servlet context
websocket One per WebSocket session 
@Component
@Scope("prototype")
public class ShoppingCart { ... }

A singleton is shared, so keep it stateless: no fields that change per user.

Spring Security

A clear guide: Spring Security explained (Marco Behler).

  • Authentication: who are you? Checking the user is who they claim to be.
  • Authorization: what may you do? Checking access to each part of the app.

Filters

Security runs as a chain of servlet filters, before any controller:

A Spring Boot app has about 15 by default, for example:

Filter Does
UsernamePasswordAuthenticationFilter Reads a username and password from a login form
BasicAuthenticationFilter Reads an HTTP Basic Authorization header
DefaultLoginPageGeneratingFilter Makes the default login page (why one appears when you add Security)
AuthorizationFilter Checks whether the user may access the URL

Configuring it

@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/", "/home").permitAll()   // open to everyone
                .anyRequest().authenticated())                // everything else needs a login
            .formLogin(form -> form.loginPage("/login").permitAll())
            .logout(logout -> logout.permitAll())
            .httpBasic(Customizer.withDefaults());            // also accept Basic auth
        return http.build();
    }
}

Older tutorials extend WebSecurityConfigurerAdapter and use antMatchers. Both were removed in Spring Security 6: declare a SecurityFilterChain bean as above.

Where the users come from

You have the passwords (your own users table): provide a UserDetailsService and a PasswordEncoder.

@Service
public class DbUserDetailsService implements UserDetailsService {
    private final UserRepository users;
    public DbUserDetailsService(UserRepository users) { this.users = users; }

    @Override
    public UserDetails loadUserByUsername(String username) {
        return users.findByUsername(username)
                .map(u -> User.withUsername(u.getUsername()).password(u.getPasswordHash()).roles("USER").build())
                .orElseThrow(() -> new UsernameNotFoundException(username));
    }
}

Ready-made alternatives: JdbcUserDetailsManager, and InMemoryUserDetailsManager for tests.

Password encoders never decrypt. They hash what the user typed and compare it with the stored hash.

@Bean
PasswordEncoder passwordEncoder() {
    return PasswordEncoderFactories.createDelegatingPasswordEncoder();   // bcrypt by default
}

The delegating encoder reads the {prefix} of each stored hash ({bcrypt}$2a$..., {sha256}...), so old and new hashes can live side by side.

Someone else has the passwords (a company directory, Atlassian Crowd): provide an AuthenticationProvider that asks that server.

Sign in with Google, GitHub...: use OAuth 2 / OpenID Connect (spring-boot-starter-oauth2-client).

The application context

The context is Spring's container: every bean your app has lives in it. When a class needs a bean, Spring finds it there. That's IoC in practice.

SpringApplication.run returns the context, so you can ask it for beans directly:

@SpringBootApplication
public class App {
    public static void main(String[] args) {
        ApplicationContext ctx = SpringApplication.run(App.class, args);
        MyController c = ctx.getBean(MyController.class);   // by type: no cast needed
        MyController same = (MyController) ctx.getBean("myController");   // by name
    }
}

A bean's default name is its class name with a lower-case first letter: MyController → "myController".

Choosing between beans

When two beans implement the same interface, Spring can't guess which one to inject and fails at startup. Three ways to decide:

@Primary: the default choice

@Component @Primary
class EmailService implements MessageService { ... }

@Qualifier: name the one you want

@Component("smsService")
class SmsService implements MessageService { ... }

class Alerts {
    Alerts(@Qualifier("smsService") MessageService service) { ... }
}

@Profile: different beans per environment

@Component @Profile("dev")
class FakeMailer implements MessageService { ... }

@Component @Profile({"prod", "default"})   // "default" applies when no profile is active
class SmtpMailer implements MessageService { ... }

Pick the profile in application.properties:

spring.profiles.active=dev

SOLID principles

Five rules for classes that are easy to change.

Principle In one line
S Single responsibility A class has one reason to change
O Open/closed Add behaviour by extending, not by editing what works
L Liskov substitution A subclass must work wherever its parent does
I Interface segregation Many small, focused interfaces beat one big one
D Dependency inversion Depend on abstractions (interfaces), not on concrete classes

Examples

  • S: a UserService that also sends emails and writes PDFs has three reasons to change. Split it into UserService, Mailer and PdfWriter.
  • O: a StudentValidator works. To validate faculty too, don't add if (faculty) branches to it: write a Validator interface with a StudentValidator and a FacultyValidator.
  • L: if a subclass needs a different kind of object in its constructor, or throws where the parent didn't, code written for the parent breaks.
  • I: a Printer interface with print(), scan() and fax() forces a simple printer to fake fax(). Split it into Printer, Scanner and Fax.
  • D: PotterMail depends on MessageService, not on EmailService. That's what makes dependency injection work.
Data: Hibernate and Mongo2 topics

Hibernate and Spring Data JPA in depth

Layer Is
JPA (Jakarta Persistence) The specification: interfaces and annotations, no code that runs
Hibernate The implementation: manages connections, generates SQL, maps rows to objects
Spring Data JPA A layer on top: you write repository interfaces; it generates the classes at runtime

Mapping annotations

Annotation Use
@Entity This class is a table
@Id The primary key
@GeneratedValue How the key is made (below)
@Column(name, nullable = false, updatable = false) Column name, NOT NULL, never updated (good for created-at times)
@Transient Not stored (e.g. an age worked out from birthDate)
@Enumerated(EnumType.STRING) Store an enum by name

ID strategies

GenerationType How Notes
IDENTITY The database's auto-increment column Simple (MySQL). Turns off JDBC batch inserts.
SEQUENCE A database sequence Fastest for batch inserts (PostgreSQL, Oracle)
UUID A random UUID Good across many services

Store enums as STRING. With ORDINAL (0, 1, 2...) reordering the enum silently corrupts your data.

Relationships

Annotation Example
@OneToOne User ↔ Profile
@OneToMany / @ManyToOne Author → many Books; each Book → one Author
@ManyToMany Students ↔ Courses, through a join table

Inheritance: Employee extends User

Strategy Tables Trade-off
SINGLE_TABLE (default) One table for all, plus a type column Fastest; subclass columns must allow NULL
JOINED One per class, joined by key Normalised; slower because of joins
TABLE_PER_CLASS One per concrete class No joins, but queries on the parent use slow UNIONs

Using JPA directly

The EntityManager is the core JPA interface:

Method Does
persist(e) Save a new entity
find(Type.class, id) Load by id
merge(e) Save changes to a detached entity
remove(e) Delete

JPQL looks like SQL but uses entity and field names:

em.createQuery("SELECT b FROM Book b WHERE b.author.lastName = :n", Book.class)
  .setParameter("n", "Ahmed")
  .getResultList();

Lifecycle hooks: @PrePersist, @PostPersist, @PreUpdate, @PostLoad... run code when an entity is saved or loaded (e.g. set createdAt).

What Spring adds

  • spring-boot-starter-data-jpa brings Hibernate and sets it up from your application.properties.
  • Repositories: query methods from names (findByTitleContaining), or @Query for JPQL.
  • @Transactional: the method runs in one transaction; an exception rolls it all back.
  • Paging and sorting: findAll(PageRequest.of(0, 20, Sort.by("title"))).
  • Specifications and the Criteria API for queries built at runtime (search forms).

Performance

  • Lazy vs eager: collections load lazily by default (only when touched). Lazy loading in a loop causes the N+1 problem: one query for the list, then one per item. Fix with JOIN FETCH or an entity graph.
  • Caching: the first-level cache (per transaction) is always on; a second-level cache (shared) is optional.

MongoDB GeoJSON (maps and locations)

The three rules

  1. Coordinates are [longitude, latitude] (x, y). Google Maps shows lat, lng: swap them.
  2. Polygon rings: the outer ring goes counter-clockwise (the shape); inner rings go clockwise (holes). The first and last points must be the same.
  3. Index the field or geo queries won't work:
    @GeoSpatialIndexed(type = GeoSpatialIndexType.GEO_2DSPHERE)
private GeoJsonPoint location;

The types

Type Is Use it for Spring Data class
Point One location A user, a shop, a vehicle GeoJsonPoint
LineString An ordered path of 2+ points, open A GPS route, a river, a street GeoJsonLineString
Polygon A closed area (min. 4 points: a triangle plus the closing point), optional holes A city boundary, a park, a geofence GeoJsonPolygon
MultiPoint Several points as one object All bus stops on route 55 GeoJsonMultiPoint
MultiLineString Several separate lines A road network with gaps GeoJsonMultiLineString
MultiPolygon Several separate areas A country with islands; a delivery zone in two parts GeoJsonMultiPolygon
GeometryCollection A mix of types A station (point) and its track (line) GeoJsonGeometryCollection

Examples

GeoJsonPoint shop = new GeoJsonPoint(-73.93, 40.73);          // x = longitude, y = latitude

GeoJsonLineString route = new GeoJsonLineString(List.of(
        new Point(-73.9, 40.7),
        new Point(-74.0, 40.8)));

GeoJsonPolygon zone = new GeoJsonPolygon(                     // counter-clockwise, closed
        new Point(0, 0), new Point(10, 0), new Point(10, 10), new Point(0, 10), new Point(0, 0));

GeoJsonMultiPoint stops = new GeoJsonMultiPoint(List.of(p1, p2, p3));
GeoJsonMultiPolygon service = new GeoJsonMultiPolygon(List.of(downtown, airport));
GeoJsonGeometryCollection mixed = new GeoJsonGeometryCollection(List.of(shop, zone));
